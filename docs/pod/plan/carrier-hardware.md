# Carrier PCB: desirable features (draft)

A custom carrier board that sits under a bare Pico 2 W (RP2350) running the pod
firmware, wiring the DUT interfaces on fixed connectors and adding the hardware
the bare Pico cannot provide (power switching, telemetry, level translation).

This is a DRAFT that lists desirable features, not a decided design. It is
deferred and gated on the software reaching GA: the current bench is a bare Pico
2 W with jumper wires to the DUT (`docs/pod/hardware-setup.md` §2), and none of
the features below are committed. Everything here is either a candidate to
evaluate or an open decision; nothing in this doc is a specification the firmware
depends on today. This is the carrier counterpart to `overview.md`'s
deferred-capabilities list (`overview.md:25-33`, `overview.md:169`).

## Why a carrier

### Remote power-cycle recovery (the strongest single driver)

The pod's worst failure mode is an external-QSPI XIP wedge that no SWD path can
clear. A flash operation that halts only core0 while core1 keeps reading flash
can interrupt an erase mid-flight and leave the QSPI chip in continuous-read/QPI
mode; the pod stops booting and Wi-Fi goes dark
(`docs/pod/dev-notes.md:47-51`; `docs/pod/plan/resume-after-power-cycle.md:9-22`).
Three software recoveries were exhausted on real hardware (bootrom
`flash_exit_xip`, a manual QMI direct-mode exit + software reset, and a
QSPI-subsystem reset); none work, because the RP2350 has no QMI-core reset bit.
Only a true power-on-reset of the flash recovers it
(`resume-after-power-cycle.md:14-22`).

The operator is remote, so today the only recovery is physical intervention. A
second, independent wedge (PIO2 corruption from a CYW43 Wi-Fi collision) is today
recovered by a USB-hub power cycle (`uhubctl -l 3-1 -p 3 -a cycle`,
`dev-notes.md:209`), but that path only exists while the pod's USB is in device
mode on a hub; once USB is in host mode for DUT forwarding, it disappears too. A
carrier that can cycle the pod's own power under software (or via an
always-reachable secondary controller) is the only way to recover the pod
remotely without human hands. This is the highest-value reason to build a
carrier.

### Other drivers

- **DUT power control for reliability soak / automated loops.** The bench-lease
  steal-sweep can release PIO blocks and named peripherals but cannot cycle the
  DUT's power rail (`docs/pod/plan/bench-lease.md:111-114`;
  `hardware-setup.md:199-203`), so a stolen or expired lease leaves the DUT in an
  arbitrary electrical state. Power-cycling the DUT between runs is standard soak
  practice and has no mechanism today without physical access. For a bus-powered
  DUT the same driver applies to its USB VBUS (see "DUT-USB power" below).
- **Telemetry.** No current/voltage telemetry exists on the bare Pico 2 W;
  INA228 per-rail sensing is deferred to the carrier (`hardware-setup.md:199-203`).
  One downstream consumer (the `aio` MicroPython asyncio-hardware roadmap, which
  uses this pod as its main HIL rig) has named current telemetry its
  critical-path hardware item; its stated requirements are recorded under
  Telemetry below.
- **Level translation.** RP2350 GPIOs are 3.3V-only and not 5V tolerant; the bare
  board's rule is to insert a shifter or divider by hand (`hardware-setup.md:35-41`).
  A carrier makes non-3.3V DUTs a first-class configuration.
- **Mechanical robustness.** Every interface is jumper-wire based today (SWD,
  I2C, GPIO/ADC, LA, backup UART, nRST, DUT UART, DUT SPI, USB host;
  `hardware-setup.md` §5a-§5j). Fixed connectors and traces remove pull-outs,
  variable contact resistance, and fast-signal integrity loss, and remove the
  need to re-verify wiring after every power cycle.

## Baseline: what the bare Pico 2 W gives us

The pinout the carrier must sit on top of is the generated diagram
`docs/pod/pinout.svg` and `docs/pod/pinout.png`. It is regenerated by
`make pinout` (`Makefile:93-95`), which runs `tools/pinout_diagram.py`; that
script reads the authoritative SWD/nRST/I2C/UART pins from
`_rp2_pinmap.pinmap()` at runtime and overlays the fixed pod extras (backup REPL,
ADC, LA block) from static tables in the script. The wiring narrative for each
interface is `docs/pod/hardware-setup.md`.

Committed pins (VERIFIED unless noted), from `src/mpy/annealage_pod/_rp2_pinmap.py`
and `hardware-setup.md:75-87`:

- Backup UART REPL (UART0): GP0 TX, GP1 RX (VERIFIED).
- DUT UART bridge (UART1): GP4 TX, GP5 RX (SUGGESTED, untested).
- I2C target (hardware I2C1, `machine.I2CTarget`): GP10 SDA, GP11 SCL (VERIFIED).
- DUT nRST (open-drain): GP13 (SUGGESTED, code-assigned, hardware-untested).
- SWD (PIO1): GP14 SWDIO, GP15 SWCLK (VERIFIED).
- Logic-analyser default block (PIO0): GP16-GP21, channels 0-5, software-configurable
  to other blocks (SUGGESTED). GP16-GP19 double as a candidate SPI0, mutually
  exclusive with the LA at runtime.
- ADC: GP26 (ADC0), GP27 (ADC1), GP28 (ADC2) (VERIFIED as ADC inputs).
- Native USB: the Pico 2 W USB connector is the DUT host port and consumes no
  GPIOs (`MICROPY_HW_USB_HOST`); no DUT has enumerated yet (SUGGESTED).
- CYW43 Wi-Fi (PIO2, internal): GP23/24/25/29 are not on the header and must
  never be touched (`hardware-setup.md:71`).

## Pin budget for the carrier

The header exposes GP0-GP22 and GP26-GP28; GP23/24/25/29 are CYW43-internal
(`hardware-setup.md:69,71`).

**Unconditionally free header GPIOs (no firmware assignment at all): 8 pins** -
GP2, GP3, GP6, GP7, GP8, GP9, GP12, GP22. These are the pins a carrier can use
today without any firmware change.

Reclaimable-with-firmware-changes GPIOs (currently SUGGESTED / default-block, not
hardware-verified): GP4, GP5 (DUT UART), GP13 (nRST), GP16-GP21 (LA default
block, of which GP16-GP19 also the candidate SPI0). A carrier could repurpose
these only if the corresponding pod function is dropped or moved, and the
firmware pinmap edited.

ADC-or-GPIO GPIOs: GP26, GP27, GP28 are VERIFIED ADC inputs but remain usable as
plain GPIO where analog measurement is not needed.

Power / ground / control rails a carrier can tap, from
`tools/pinout_diagram.py:59-98` and `hardware-setup.md:97-127`:

- VBUS (header 40): USB 5V; source/path is open now that the pod's USB is a host.
- VSYS (header 39): main 3.3V-regulator input (2-5V); the safe pod power inlet
  when native USB is a host.
- 3V3(OUT) (header 36): regulated 3.3V out; can power a small DUT.
- 3V3_EN (header 37): pull low to disable the regulator (shuts the RP2350 down).
- ADC_VREF (header 35): ADC reference, normally tied to 3V3(OUT).
- RUN (header 30): the pod's own active-high reset; pull low to reset the RP2350.
- GND: 8 pins (headers 3, 8, 13, 18, 23, 28, 33, 38).

There is no GP29/ADC3 on the header; the internal temperature sensor is on ADC4
(not a pin). The 8-free-pin budget is the hard constraint on how much a
zero-firmware-change carrier can add; anything more competes with the SUGGESTED
functions above.

## Desirable features

Priorities are rough and provisional.

### Power domain

**DUT power-rail switching / remote power-cycle recovery (HIGHEST priority).**
A software-controllable switch on the pod's own power (VSYS rail, or a secondary
always-reachable controller driving a MOSFET) so the operator can recover the
XIP-wedge brick and the PIO2 wedge remotely (see "Why a carrier"). This is the
one feature that addresses the pod's worst failure mode.
Interface: a load switch or PFET on VSYS/VBUS (headers 39/40) with 3V3_EN
(header 37) and RUN (header 30) as adjacent pod-reset controls; if driven from
the RP2350 itself it needs one of the free GPIOs, but self-cycling the pod that
is itself wedged is the design tension (see open decisions). Prior art: the
ESP32-S3 VTARGET/DUT-USB load switches (MT9700 / TPS2595, 5 V/s ramp) each on a
separate GPIO (S3 spec §3.3).

**DUT power-rail switching (soak / lease sweep).** A controlled switch on the DUT
supply so the bench-lease steal-sweep and automated loops can bring the DUT to a
known state (`bench-lease.md:111-114`; `hardware-setup.md:199-203`). Maps to the
`power` reset mode currently gated on the carrier (`overview.md:80,135`;
`phase-5-peripherals-telemetry.md:317-320`). Priority: high. Interface: a load
switch on the DUT rail, one control line (free GPIO or the carrier controller).
Prior art: the S3 VTARGET ramped switch and the `reset(mode='power')` path
(S3 spec §3.3-§3.4).

**DUT-USB VBUS.** The USB-host VBUS rail spans both control (switching, inrush,
sequencing) and measurement (present detect, current draw), so it is treated as
a single capability in "DUT-USB power" below rather than split between this
section and Telemetry. It remains one of the rails per-rail control (next)
sequences.

**Per-rail control.** Separate switches per DUT rail (e.g. VTARGET vs the
DUT-USB VBUS, "DUT-USB power" below) rather than one master, so rails can be
sequenced. Priority: medium. Interface: one control line per rail. Prior art:
the S3 design's independent VTARGET and DUT-USB switches.

**Pod self-recovery (feasibility open).** Whether the carrier can cycle the pod's
own power from the pod is fundamentally limited when the pod is the thing that is
wedged; a watchdog-gated switch or a small always-on secondary controller is the
candidate. Priority: high but feasibility-gated. Prior art: none in-tree; the S3
watchdog tiers (S3 spec §6.2) are the nearest reference but do not cover power
cycling.

### DUT-USB power (control and measurement)

USB power to the DUT is one capability with two halves: control (switching the
VBUS the pod's host port supplies to a bus-powered DUT) and measurement (seeing
what that VBUS is doing). Both halves are candidates like everything else here,
but they are load-bearing for the pod's headline use cases, so they are
specified together in this section; Power domain and Telemetry point in rather
than carrying their own halves. The VBUS source, cabling, and current limit are
open hardware decisions today (`hardware-setup.md:271-282,293-296,334-335`).
Three use cases drive it:

- **Remote recovery of a bus-powered DUT.** With a carrier VBUS switch, the
  host can cut and restore DUT-USB VBUS under software, power-cycling a wedged
  bus-powered DUT with no physical access. The rig's only remote USB
  power-cycle today is the workstation-hub cycle (`uhubctl -l 3-1 -p 3 -a
  cycle`, `dev-notes.md:209`), and that path exists only while the pod's USB is
  a device on that hub; once the native USB is the DUT host port for
  forwarding, it is gone (see "Why a carrier"). A carrier-driven VBUS switch is
  what restores a software USB power-cycle path, aimed at the DUT rather than
  the pod.
- **Reliability soak / automated loops.** Power-cycling the DUT between test
  runs, and bringing a stolen or expired bench lease back to a known electrical
  state (`bench-lease.md:111-114`), applies to a bus-powered DUT via its VBUS
  exactly as it applies to the DUT supply via the VTARGET switch (Power domain
  above).
- **Bring-up sequencing.** VBUS is raised only after the USB host stack is
  running, so the DUT never sees a live bus with a dead host. This matches the
  S3 order: host stack first, then VBUS (S3 spec §3.3; usbhost.md §10).

**VBUS switching (control).** A software-controlled load switch on the USB-host
VBUS so a bus-powered DUT can be powered, cut, and restored under host command.
Priority: high (the USB-host power path is an open hardware decision today,
`hardware-setup.md:271-282,293-296`). Interface: a load switch on the USB VBUS,
one control line (free GPIO or the carrier controller). Prior art: the S3
TPS2595/MT9700 load switch on DUT-USB VBUS (S3 spec §3.3).

**Inrush, current limit, and sequencing (control).** The switch should be a
real load switch, not a bare FET: a controlled ramp so a capacitive DUT does
not sag the rail at turn-on (the S3 used a 5 V/s ramp), a current limit sized
for the USB power budget, and the defined power sequence against the host stack
(stack first, then VBUS, per the S3 order above). An overcurrent fault flag
readable by the firmware (GPIO or carrier controller) is a further candidate,
so the host learns about a shorted or over-budget DUT rather than seeing a
silent rail droop; fault reporting has no in-tree prior art. Priority: high
(travels with the switch). Prior art: the S3 TPS2595/MT9700 with the 5 V/s ramp
(S3 spec §3.3).

**VBUS sensing (measurement).** The measurement half: vbus-present detect (is
the USB-host VBUS live) and VBUS current draw (what the DUT pulls, including
enumeration-time inrush), so the host can see the DUT's USB power state without
physical probes. In the S3 design both come off the second INA228:
`power.dut_usb.vbus_present()` reads the INA228 VBUS voltage register rather
than a dedicated ADC pin, because the S3's ADC2/Wi-Fi conflict ruled out analog
sense (S3 spec §7.2 for the API, §3.3 for the rail, §8 open-item 8 for the
conflict; `phase-5-peripherals-telemetry.md:314`). The RP2350 ADC/Wi-Fi
tradeoff would need its own check before choosing a spare ADC pin (GP26-28)
over the INA228 register. Priority: medium (present detect) / high (current,
shared with the Telemetry INA228 entry). Interface: the DUT-USB INA228 on the
local carrier I2C bus (see Telemetry), or a spare ADC for present-detect only.
The per-rail sensor itself and its resolution requirements live under
Telemetry; this entry is the USB-specific consumer of it.

### Telemetry

**INA228 per-rail current/voltage.** Per-rail current and bus voltage on VTARGET
and DUT-USB VBUS via portable INA228 drivers (reused, not rewritten), the
telemetry surface deferred to the carrier (`overview.md:26`;
`phase-5-peripherals-telemetry.md:312-315`; `hardware-setup.md:199-203`).
Priority: high. Interface: I2C (a local carrier I2C bus, distinct from the
DUT-facing I2C target on GP10/GP11). Prior art: two INA228s, one per rail, on a
local I2C bus in the S3 design (S3 spec §3.3, §7.2); the INA228 driver is named as
shared code (`overview.md:109`) and lives at `src/mpy/annealage_pod/_ina228.py`.
The DUT-USB rail's measurement consumers (vbus-present detect, enumeration-time
inrush) are specified under "DUT-USB power" above; the downstream requirement
below constrains the front-end choice for the VTARGET rail.

**DUT-USB VBUS sensing.** Covered under "DUT-USB power" above (vbus-present
detect plus VBUS current draw, including the S3's INA228-register-vs-ADC-pin
choice and the RP2350 ADC/Wi-Fi check). It shares the local-I2C INA228
infrastructure of the previous entry; listed here so the telemetry inventory is
complete.

**Downstream consumer requirement: sleep-current measurement (aio roadmap).**
The `aio` MicroPython asyncio-hardware roadmap, which uses this pod as its main
HIL rig, has stated concrete requirements for the current-telemetry front-end.
These are external asks from that consumer, deliberately not cited to an
in-tree source because none exists yet; they are recorded here because they
carry hardware lead time:

- Current measurement is their critical-path hardware item: everything else on
  their roadmap has a software workaround, this one does not.
- Over a measurement window, the telemetry tool must return the windowed mean
  plus min/max plus integrated energy, not just an instantaneous sample, so a
  sleep/STOP/lightsleep-entry current can be diffed against an active baseline.
- Resolution sub-mA, ideally sub-100 µA: MCU sleep-state currents are that
  small, and "idle current drops measurably" is their flagship acceptance
  criterion, so the shunt/sense front-end and the ADC/averaging must resolve
  sleep-state deltas.

The requirement lands on both sides of the interface: the carrier hardware
(shunt value, INA228 versus a higher-gain front-end, averaging configuration)
and the eventual telemetry tool's output shape (windowed statistics, not point
samples). It directly informs the INA228 choice above and the
current-sense-resolution open decision below.

**Sample-at-rate analog capture + analog stimulus (candidate, distant).** The
bare board's `adc` is single-shot voltage only. The same `aio` consumer wants,
for a later phase (Phase 6, lowest priority), sample-at-rate analog CAPTURE for
DAC-streaming verification and a known analog waveform SOURCE for ADC-continuous
verification (a PWM + filter on the pod would serve as the source). This is a
further front-end beyond the INA228 power path. The pod's own ADC pins
(GP26-GP28) plus a PWM-derived analog output could prototype both halves before
any dedicated carrier front-end exists. Priority: low (the consumer places it
distant). Interface: a timed-ADC capture path and a PWM+filter analog output;
carrier front-end TBD. No in-tree prior art; external ask, not cited to a
repo source.

### Level translation

**Configurable DUT logic levels.** Bidirectional level translation on the
DUT-facing signals (SWD SWDIO/SWCLK, UART, I2C, GPIO, and the LA taps) so a 5V or
1.8V DUT is supported rather than requiring a hand-inserted shifter
(`hardware-setup.md:35-41`). Level translation is named as a carrier-gated
capability (`overview.md:31-32`) but is not otherwise broken out in the phase
docs, so its scope here is a candidate, not a settled requirement. Priority:
medium-high (depends on whether non-3.3V DUTs are in the target set). Interface:
direction-controlled translators referenced to the DUT logic supply; the SWD line
needs correct per-frame direction handling. Prior art: the S3's
74LVC1T45-style direction-controlled translators with the B-side referenced to
VTARGET, and per-frame SWDIO direction control (S3 spec §3.2, §4.6). Note the S3
made VTARGET programmable only at rev2 (3.3V fixed at rev1); a programmable DUT
logic level is a further open decision here.

### Signal switching / relays

**Opto-relay bank (candidate to reconsider; currently OUT of scope).** The
ESP32-S3 carrier carried 7 opto-coupled relays (Octoprobe v0.7 heritage) driving
boot-button holds, BOOT0/BOOT1 mode pins, and DUT-specific patterns like
BOOTSEL+RESET sequences (S3 spec §3.4). On the RP2350 this is explicitly OUT of
scope: "Opto-relays are out of scope for this design" (`overview.md:33`), and the
S3 `relay` reset path is dropped (`phase-3-gdb-debug-control.md:33`). Listed here
only so a carrier design can deliberately reconsider whether any relay-driven
boot-mode control is worth reintroducing; the default remains no. Priority: low.
Interface: one control line per relay (would draw on the 8-free-pin budget or the
carrier controller). Prior art: `annealage_pod.relays` / the `set_relays` RP_INFRA
mimic in the S3 package.

### Connectors and mechanical

**Fixed DUT connector.** A proper connector (or connectors) carrying SWD, UART,
I2C, GPIO/ADC, and the LA taps so the DUT wiring is a plug, not a jumper harness
(`hardware-setup.md` §5a-§5i). Priority: high. Interface: routes the committed
pins above to a connector footprint. Prior art: the S3 carrier's per-function
connectors (e.g. J501 for the relay bank).

**USB-host cabling and power.** A defined USB-host connector plus the VBUS source
and current limit for a bus-powered DUT, which are open decisions today
(`hardware-setup.md:271-282,293-296,334-335`). Priority: high (blocks the
USB-host power model). Interface: a host-side USB connector and the VBUS switch
from "DUT-USB power" above. Prior art: the S3 J202 USB-A receptacle with a
load-switched, INA228-monitored VBUS (S3 spec §3.1, §3.3; usbhost.md §10).

**Pod socket + robustness.** A fixed socket for the Pico 2 W and traced signal
routing, replacing the breadboard/jumper topology so the assembled unit survives
cable drag and stays connected across power cycles (`hardware-setup.md` §2).
Priority: high. Interface: mechanical.

### Protection

**ESD, current limiting, reverse-polarity.** On-board protection on the DUT-facing
lines and power inlets: ESD clamps on exposed signals, current limiting on the
switched rails (the load switches above provide part of this), and
reverse-polarity protection on any external power inlet. Today the only stated
electrical guard is the manual 3.3V-only rule (`hardware-setup.md:35-41`).
Priority: medium. Interface: passive/active protection at connectors and inlets.
Prior art: current limiting is implicit in the S3 load switches (S3 spec §3.3);
ESD/reverse-polarity are not separately documented in-tree.

### Carrier identity

**carrier-id auto-detect.** A way for the firmware to auto-detect which carrier is
present and report it. The `carrier-id` field is already wired into the mDNS TXT
record (`phase-1-foundation.md`, F1.3) and the pod registry
(`phase-6-host-tooling-mcp.md`, H6.1; `spike-findings.md:90-96`); on a bare Pico
2 W it is empty or a bare-board sentinel, and only gains meaning when a carrier
exists. Priority: medium (cheap to add, closes the loop on an already-planned
field). Interface: an I2C ID EEPROM on the local carrier bus, or strapping
resistors on free GPIOs / an ADC divider. Prior art: the S3 carrier-ID EEPROM on
the local I2C bus, published as `annealage_pod.carrier.id()` (S3 spec §3.6).

## Open decisions

- **Form factor.** HAT-style board the Pico 2 W plugs into, versus a custom board
  the Pico is soldered/socketed onto. Undecided.
- **How many rails.** One DUT rail, or separate VTARGET and USB-VBUS rails
  (per-rail control above), and whether the pod's own rail is switchable for
  remote recovery. Undecided.
- **Which logic levels.** Fixed 3.3V translation, a fixed alternate (5V / 1.8V),
  or a programmable DUT logic supply (the S3 deferred this to rev2). Undecided.
- **Power the DUT or only switch it.** Whether the carrier sources the DUT supply
  (regulator on-board) or only gates an external supply
  (`hardware-setup.md:289-296`). Undecided.
- **Current-sense resolution / front-end.** Whether an INA228 with an
  appropriately sized shunt and averaging configuration resolves the sub-100 µA
  sleep-state currents the aio consumer requires (see the downstream requirement
  under Telemetry), or whether a higher-gain or dual-range front-end is needed;
  and the shunt-value tradeoff between resolution, full-scale range, and burden
  voltage on the DUT rail. Undecided.
- **Analog capture / stimulus front-end.** Whether the carrier carries a
  sample-at-rate analog capture path and a waveform source (PWM + filter) for the
  aio Phase-6 analog verification, or whether the pod's own ADC (GP26-GP28) plus a
  PWM output suffice. Distant; undecided.
- **Opto-relays.** Whether any relay-driven boot-mode control returns; the current
  answer is no (`overview.md:33`).
- **Connector choice.** Single combined DUT connector vs per-function connectors,
  and the USB-host connector type / VBUS source / current limit
  (`hardware-setup.md:334-335`). Undecided.
- **Pin-assignment conflicts.** The 8-free-pin budget (GP2, GP3, GP6, GP7, GP8,
  GP9, GP12, GP22) is small. Rail switches, VBUS switch, translator DIR lines,
  relays, and carrier-id strapping all compete for it unless the SUGGESTED
  functions (DUT UART, nRST, LA block) are reclaimed with firmware changes, or a
  secondary I2C-attached controller offloads the control lines onto its own pins.
  Which control lines go on RP2350 GPIOs versus a carrier-local controller is
  undecided.
- **Pod self-recovery feasibility.** Whether a wedged pod can cycle its own power
  at all, or whether an always-on secondary controller is required. Undecided.
