Pre-R21 baseline (post-R20, commit 9c19f30 + R20 plans).

Hardware: ESP32-S3 (mpy-dev "esp32-s3", serial 5A45040839) USB-host to
RP2040 Pico running stock MicroPython, exposed via usbip 1-1, attached
on the host with `sudo usbip attach -r 192.168.0.166 -b 1-1`.

Generated by:
  test/integration/phase3/cdc_throughput.py \
    /dev/serial/by-id/usb-MicroPython_Board_in_FS_mode_a5a2229740635c53-if00

DATA IN (device->host) only. Pico's stdin ringbuffer caps the
host->device direction at a non-USB-related throughput so OUT was not
captured. Echo test was skipped (RP2 stdin lacks readinto).

  bufsize=256    nbuf=128  rate=11417      kib_s=11.1
  bufsize=512    nbuf=44   rate=11228      kib_s=11.0
  bufsize=1024   nbuf=21   rate=10949      kib_s=10.7
  bufsize=2048   nbuf=10   rate=10366      kib_s=10.1
  bufsize=4096   nbuf=5    rate=7470       kib_s=7.3
  bufsize=8192   nbuf=1    rate=5667       kib_s=5.5
  bufsize=16384  nbuf=1    rate=5592       kib_s=5.5

Notes:
- All numbers are well below the FS bulk wire ceiling (~1.2 MB/s).
- Throughput trends down with larger bufsize, suggesting the Linux
  cdc-acm read URB is sized small (likely 2 * MPS = 128 bytes) and
  larger device-side writes are split into many small URBs whose
  per-URB overhead dominates the cost.
- R21 should target this gap.

Direct-Pico reference baseline (added 2026-05-01 after R21).

The same benchmark run against pico2-w (Pico 2 W with RP2350,
also FS-only) plugged directly into the host PC, NOT going through
the ESP32-S3 middlebox. Same kernel cdc-acm driver, same 128-byte
URBs. The 65x gap vs the via-USB/IP numbers above proves the
cdc-acm readsize is NOT the bottleneck; the gap is in our middlebox.
